# セキュリティレビュー

## 第2回(2026-11-02、β版の時点)

第1回の後に足した機能(先攻・後攻、勝敗、次のデュエル・やり直し、通算の戦績、LP 入力の式)を含めて、もう一度、攻撃者の立場から見直した。一度開いた部屋をどう扱うか(部屋のライフサイクル)も観点に加えた。

### 修正したもの

| # | 深刻度 | 問題 | 対策 |
|---|---|---|---|
| 1 | 中 | **席の乗っ取り**。席を取り戻すための `clientId` が、参加者一覧と状態に入って全員に配られていた。そのため、リンクから観戦者として入った3人目が P2 の `clientId` を名乗ると、P2 が接続中でも P2 の席を奪えた | 他の端末に送る参加者一覧と状態から `clientId` を外した(`PublicMember`、`publicState`)。`clientId` はホストだけが持つ |
| 2 | 低 | **受信した状態を確かめていなかった**。ゲストはホストからの状態をそのまま使っていたので、ホストを乗っ取った人が壊れた状態を送ると、ゲストの画面が落ちた | `normalizeState` で型と範囲を確かめ、表示に使う項目を既定値で補う。保存データの読み込みにも同じ処理を使う |

| 3 | 中 | **部屋に終わりがない**。招待リンクはずっと有効で、閉じる手段もなかった。ホストがいなくなった後も保存データが残り、同じ URL を開くといつでも再開できた | ホストに「部屋を閉じる」ボタンを付けた。押すと全員に通知して切断し、保存データとカメラ用の合言葉を消す。閉じられたことを知ったゲストやカメラ端末は、再接続しない |
| 4 | 低 | **保存データが消えない**。部屋ごとの状態(名前・履歴・戦績)が、ホストのブラウザに期限なしで残っていた。共有の PC だと次の人に見える | 保存データに保存日時を付け、最後に使ってから1日たったものは読み込まずに消す。起動時にも、期限切れのデータや保存日時のない古い形式のデータをまとめて消す |
| 5 | 低 | **カメラ用の合言葉を作り直せない**。カメラ用リンクが漏れても、ホストのタブを開き直すまで無効にできなかった | 「スマホをカメラにする」の画面に「合言葉を作り直す」を付けた。作り直すと、古い合言葉で接続中のカメラ端末は切断され、以後も入れない |

### 確認して問題がなかったもの

- 勝敗・次のデュエル・やり直し・戦績のリセットを、ゲストからの操作として送る場合も、ホストの `parseAction` で検証している(勝者は席か引き分けだけ、理由は決まった値だけ)。
- LP 入力の式は `eval` を使わず、四則演算と括弧だけを解釈している。長さは 100 文字まで。
- `npm audit` は 0 件。GitHub Actions の既定の権限は読み取りだけで、シークレットは使っていない。シークレットスキャンとプッシュ保護は有効。

### 受け入れたリスク(追加分)

- **一度開いた部屋のホストの乗っ取り**: ホストがタブを閉じている間や部屋を閉じた後に、招待リンクを持つ人が `&host=1` を付けて開くと、同じ部屋 ID のホストになれる。その後に入ってきたゲストの操作とカメラ映像を受け取れる。部屋 ID は接続仲介サーバー上で早い者勝ちのため、ツールだけでは防げない。防ぐには、ゲストが初回に接続したホストの公開鍵を覚えておき、再接続のたびに署名で本人確認する仕組みが要る。今回は見送り、閉じた部屋の招待リンクは使わないよう画面で案内するだけにした。
- **P2 の席は空いていれば誰でも入れる**: P2 が退出している間は、招待リンクを持つ人が P2 として入れる。席の取り戻しに使う `clientId` はタブごとなので、元の P2 がタブを閉じてから入り直した場合も、新しい人として扱われる。

- **ゲストへの映像の通話**: ピア ID を知っている人は、誰でも映像の通話を送れる。ピア ID は、同じルームの参加者一覧でしか見えない。受け取った映像は、ホストが割り当てた席と結び付かないかぎり表示しないが、通話には応答するので帯域は使われる。参加者一覧が届く前に正しい通話が来ることもあるため、応答を拒むと正しい映像まで取りこぼすおそれがある。そのため、今は応答したうえで表示しない形にしている。
- **勝敗や戦績は誰でも変えられる**: 席のあるプレイヤーなら、どちらでも勝敗の確定や戦績のリセットができる。身内で使う前提の自己申告制で、間違いは「1手戻す」で直せる。
- **Dependabot が無効**: 依存の脆弱性の自動通知と自動修正が、リポジトリの設定で無効になっている。有効にするかどうかは持ち主が決める。

## 第1回(2026-11-02、公開前)

公開前に、攻撃者の立場から穴を探すレビュー(対立的レビュー)を行った。前提とした攻撃者は次の3通り。

- 招待リンク(ルーム URL)を手に入れた第三者
- 悪意のある対戦相手
- 通信経路や外部サービス(PeerJS の公開シグナリングサーバー)

## 修正したもの

| # | 深刻度 | 問題 | 対策 |
|---|---|---|---|
| 1 | 高 | **スナップショット経由の XSS**。送信側が `mime` を `text/html` にして HTML を送ると、受信側で `blob:` URL として開いたときに、このサイトの権限でスクリプトが動く | 受け取る `mime` を `image/jpeg` `image/png` `image/webp` に限る。データが ArrayBuffer であること、10MB 以下であることも確かめる |
| 2 | 中 | **偽のカメラ映像の差し込み**。リンクを知っていれば誰でも「カメラ端末」として参加でき、映像に付ける席(`seat`)も送信側が自己申告していた | カメラ端末用リンクに、プレイヤーごとの合言葉(128 ビット)を入れ、ホストが照合する。映像の席は自己申告を使わず、ホストが配る参加者一覧から引く |
| 3 | 中 | **操作データの未検証**。ゲストが送る操作をホストがそのまま処理しており、LP の `NaN` 化、`__proto__` を席として使った状態の破壊、チェーンの無限追加などができた | `parseAction` で型と範囲を検証する。LP は 0〜999,999、チェーンは最大 30 個、文字列は長さに上限を設ける。`hello` の各フィールドも検証する |
| 4 | 低〜中 | **観戦者にもカメラ映像が届く**。満員のあとに入った3人目にも映像が送られていた | 席のない参加者には映像を送らない |
| 5 | 低 | **ルーム ID が短い**(6 文字、約 30 ビット) | 10 文字(約 49 ビット)にした |
| 6 | 低 | **CSP がない** | 本番ビルドに CSP を入れた。スクリプトは自サイトのものだけ、通信先は自サイトとシグナリングサーバーだけに限る |
| 7 | 中(開発時のみ) | 開発用の vite・esbuild に、既知の脆弱性がある(開発サーバーからファイルを読み取られるなど) | vite を 6.4.5 に更新。`npm audit` は 0 件 |

## 受け入れたリスク(身内で使う前提のため、現時点では対策しない)

- **招待リンクを持つ人は誰でも参加できる**: 認証がないので、リンクが漏れると、P2 が不在のあいだに P2 として入れる。リンクは信頼できる相手にだけ送る。
- **ホストの乗っ取り**: ホストがページを閉じているあいだに、リンクを持つ人が `&host=1` を付けて開くと、ホストの ID を先に取れる。対策するには公開鍵でホストを確かめる仕組みが要るので、必要になったら検討する。
- **IP アドレスが相手に見える**: WebRTC の P2P 接続の性質上避けられない。隠したい場合は、TURN の中継だけを使う設定にする必要がある。
- **シグナリングサーバーを信頼している**: PeerJS の公開サーバーは接続の仲介をするだけで、映像やデータの中身は通らない(DTLS で暗号化)。ただし、サーバーが悪意を持てば、仲介の段階で割り込める。気になる場合は自前の PeerServer を立てる(`VITE_PEER_HOST`)。
- **GitHub Actions のバージョンをタグで指定している**(`@v4` など): コミットのハッシュでは固定していない。公式の actions だけを使っているので許容する。
