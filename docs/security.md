### 受け入れたリスク(追加分)

- **名乗らない接続で入室を妨げられる**: 名乗る前の接続に上限を付けたので、招待リンクを持つ人がこの枠を埋め続けると、他の人が入りにくくなる。ホストの資源を使い切られるよりはよいので受け入れる。
- **大きなメッセージの大きさは制限していない**: PeerJS が組み立てた後に受け取るので、ツールの側では組み立て中のデータを制限できない。
- **ホストの ID を取られると部屋に戻れない**: 招待リンクを持つ人が先にホストの ID を取ると、本物のホストは接続できず、部屋の作り直しになる。ゲストの情報は渡らないが、妨害は防げない。
- **別の端末へはホストを移せない**: 秘密鍵は部屋を作ったブラウザにしかない。同じブラウザなら、タブを閉じた後でも戻れる。
- **映像の通話には署名を結び付けていない**: 映像は別の接続を使うので、悪意のある仲介サーバーなら映像だけは割り込める。ホストの確認は防げる。

- **改ざんされたビルド結果は公開される**: #9 は権限を減らすだけで、`build` ジョブが依存パッケージに乗っ取られた場合は、その結果がそのまま公開される。

## 映像の向きの追加時(2026-11-02)

スマホを縦に置くと縦長の映像が届き、横長の枠では見づらいので、カメラ端末で映像の向きを 90° ずつ回せるようにした。映像そのものは加工せず、向き(0・90・180・270)だけをホストに伝え、ホストが参加者一覧に載せて配る。見る側は、その角度で回して表示する。カメラ端末の画面には、全画面にして横向きに固定するボタンも付けた(iPhone の Safari は対応しないので、手で横に持つよう案内する)。

| 観点 | 内容 |
|---|---|
| ゲストから届くデータ | 新しいメッセージ `rotate` を受け付けるのは、合言葉で入ったカメラ端末からだけ。値は 0・90・180・270 に丸め、それ以外は 0 として扱う。変わったときだけ参加者一覧を配り直す |
| 他の端末に配る情報 | 参加者一覧のカメラ端末の行に `rotate` が増えた。見る側でも同じように丸めてから、表示のクラス名に使う |
| 部屋のライフサイクル | 向きはカメラ端末の接続ごとにホストが持ち、切断で消える。端末側は自分の向きを localStorage に覚え、つなぎ直したら送り直す |
| PC から回す | 持ち主は、自分の PC の「自分のカメラ」欄や拡大表示から回せる。新しいメッセージ `camRotate` は、送ってきた人の `clientId` が、そのカメラ端末の持ち主(合言葉を作った人)と一致するときだけ受け付ける。他の人のスマホは回せない。ホストはカメラ端末にも向きを伝え、端末の表示と保存を合わせる(端末からホストへは送り返さない) |

**受け入れたリスク**: 高画質スナップショットは、回した向きで表示するだけで、保存した画像は元の向きのまま。

## 席の入れ替えの追加時(2026-11-02)

ホストを P1 に固定するのをやめ、誰でも(ホストも)観戦に回ったり、空いた席に座ったりできるようにした。ユーザーと決めた方針は次のとおり。

- 入れ替えられるのは、決着後か、まだ何もしていないデュエル(LP・ターン・フェイズ・チェーンが開始時のまま)のときだけ。
- 席は自分でしか動かせない。ホストも、他の人を席から降ろせない。
- 戦績は席ではなく、名前ごとに数える。
- スマホのカメラ端末は、席ではなく持ち主(合言葉を作った人)に付いていく。持ち主が観戦中は映像を送らない。

### 入れ替えた仕組み

| 観点 | 対策 |
|---|---|
| 席の検証 | 席の移動はゲストからの申請(`seat`)として受け取り、ホストが判定する。座っている人がいる席には移れない。デュエル中は、席から降りることも、席を移ることもできない。カメラ端末は申請できない |
| 1手戻す | 戻すときは、席の持ち主(`clientId` と名前)だけは今のままにする。交代した後に戻すと、前の人に席の権利が戻ってしまうため |
| 名乗り直し | `hello` は接続ごとに1回だけ受け付ける。同じ接続で `clientId` を替えて名乗り直し、席を2つ取るのを防ぐ |
| カメラの合言葉 | 合言葉は席ではなく `clientId` ごとに持つ。カメラ端末の席は、持ち主の今の席から毎回引く。席のない人の合言葉は、その人が抜けたら忘れる(接続を繰り返して表を膨らませられないように)。回線が切れた人の席を他の人が引き継いだら、前の持ち主の合言葉も忘れる |
| 観戦の上限 | 観戦中のホストも、4人の上限に数える(ホストにも映像を送るため)。席から観戦に回るときも上限を確かめる |

### 受け入れたリスク(追加分)

- **空いた席はデュエル中でも観戦者が座れる**: 回線が切れた人の復帰や代打のため。これまで P2 だけにあったリスク(招待リンクを持つ人が、切断中の P2 に入れる)が、P1 にも広がった。ホストが観戦中や切断中の P1 にも、他の人が座れる。座る前に「〇〇は回線が切れています」と確認を出す。
- **席に居座る人をどかせない**: 席は自分でしか動かせない方針のため。どうしても困るときは、部屋を閉じて作り直す。
- **戦績は名前の自己申告**: 名前を他の人と同じに変えれば、その人の勝ちとして記録される。勝敗そのものも自己申告制なので、範囲は変わらない。
- **デュエル開始前の判定は盤面で行う**: 席にいる人が LP やフェイズを開始時に戻せば、入れ替えられる状態になる。ただし自分の席しか動かせないので、他の人への害はない。

### 参加者一覧の追加時

席の欄を参加者一覧にし、誰がホストか、どの席にスマホのカメラ端末がつながっているかを表示した。他の端末に新しく配る情報は、参加者一覧の `host`(ホストかどうか)だけ。ホストの peerId はもともと部屋 ID から決まるので、新しく知られることはない。カメラ端末の数は、以前から参加者一覧の `role: 'camera'` で配っていた。ゲストからホストに届くデータは増えていない。`host` は表示に使うだけで、退出させる操作の可否は、これまでどおりホストの側で判定する。

## 観戦機能の追加時(2026-11-02)

観戦機能を足すにあたり、ゲストから届くデータの検証、他の端末に配る情報、部屋のライフサイクルの3つの観点で見直した。ユーザーと決めた方針は次のとおり。

- カメラ映像は、観戦者にもカメラ端末から直接送る。第1回で決めた「観戦者に映像を送らない」は、この方針に置き換える。
- 招待リンクは1つのままで、開いた人が「対戦する/観戦する」を選ぶ。
- ゴースト(観戦者が片方のプレイヤーに情報を流すこと)の対策はしない。観戦者も高画質スナップショットを使える。

### 入れた対策

| 観点 | 対策 |
|---|---|
| 送信の負担 | 観戦者は4人まで(`SPECTATOR_MAX`)。カメラ端末は見る人の数だけ映像を送るので、上限がないとプレイヤーへの映像まで劣化する。上限を超えた人には理由を返して切断し、自動では再接続させない |
| ゲストからのデータ | 観戦者からの操作(`intent`)と合言葉の変更(`camKey`)は、ホストが役割と席を見て捨てる。`hello` の役割は `player` / `camera` / `spectator` だけを受け付ける |
| ライフサイクル | ホストは観戦者を一覧で確認し、退出させられる。退出させた人には理由を返し、自動では再接続させない。部屋を閉じたときは、観戦者にも通知して切断する |

### 受け入れたリスク(追加分)

- **観戦者が P2 の席を取れる**: 入るときの選択は自己申告なので、P2 が空いているときに「対戦する」を選べば P2 になれる。身内向けとして受け入れた。
- **退出させても入り直せる**: 退出は、その接続を切るだけ。招待リンクを開き直せば、また入れる。完全に締め出すには、部屋を閉じて作り直す。
- **ゴースト**: 対策しない(上記の方針)。
- **観戦者にも参加者一覧の peerId が届く**: 届いた映像の席を判定するのに使うため。以前からの「peerId を知っていれば映像の通話を送れる」というリスクの範囲は変わらない(観戦者も招待リンクを持つ人)。

### この見直しで見つけた不具合

- **高画質スナップショットが届かなくなっていた**: 第1回の XSS 対策で「受け取るデータは ArrayBuffer に限る」としたが、PeerJS は大きなデータを分割して送り、受け取る側で Uint8Array として組み立てる。そのため、正しいスナップショットまで「不正」として捨てていた。ArrayBuffer と Uint8Array などの型付き配列の両方を受け付けるよう直した。画像の種類と大きさの確認は残している。第1回の修正の後に、スナップショットを試し直していなかったのが原因。

### 確認して問題がなかったもの

- 勝敗・次のデュエル・やり直し・戦績のリセットを、ゲストからの操作として送る場合も、ホストの `parseAction` で検証している(勝者は席か引き分けだけ、理由は決まった値だけ)。
- LP 入力の式は `eval` を使わず、四則演算と括弧だけを解釈している。長さは 100 文字まで。
- `npm audit` は 0 件。GitHub Actions の既定の権限は読み取りだけで、シークレットは使っていない。シークレットスキャンとプッシュ保護は有効。

### 受け入れたリスク(追加分)

- **一度開いた部屋のホストの乗っ取り**: ホストがタブを閉じている間や部屋を閉じた後に、招待リンクを持つ人が `&host=1` を付けて開くと、同じ部屋 ID のホストになれる。その後に入ってきたゲストの操作とカメラ映像を受け取れる。部屋 ID は接続仲介サーバー上で早い者勝ちのため、ツールだけでは防げない。防ぐには、ゲストが初回に接続したホストの公開鍵を覚えておき、再接続のたびに署名で本人確認する仕組みが要る。今回は見送り、閉じた部屋の招待リンクは使わないよう画面で案内するだけにした。
- **P2 の席は空いていれば誰でも入れる**: P2 が退出している間は、招待リンクを持つ人が P2 として入れる。席の取り戻しに使う `clientId` はタブごとなので、元の P2 がタブを閉じてから入り直した場合も、新しい人として扱われる。

- **ゲストへの映像の通話**: ピア ID を知っている人は、誰でも映像の通話を送れる。ピア ID は、同じルームの参加者一覧でしか見えない。受け取った映像は、ホストが割り当てた席と結び付かないかぎり表示しないが、通話には応答するので帯域は使われる。参加者一覧が届く前に正しい通話が来ることもあるため、応答を拒むと正しい映像まで取りこぼすおそれがある。そのため、今は応答したうえで表示しない形にしている。
- **勝敗や戦績は誰でも変えられる**: 席のあるプレイヤーなら、どちらでも勝敗の確定や戦績のリセットができる。身内で使う前提の自己申告制で、間違いは「1手戻す」で直せる。
- **Dependabot が無効**: 依存の脆弱性の自動通知と自動修正が、リポジトリの設定で無効になっている。有効にするかどうかは持ち主が決める。

## 受け入れたリスク(身内で使う前提のため、現時点では対策しない)

- **招待リンクを持つ人は誰でも参加できる**: 認証がないので、リンクが漏れると、P2 が不在のあいだに P2 として入れる。リンクは信頼できる相手にだけ送る。
- **ホストの乗っ取り**: ホストがページを閉じているあいだに、リンクを持つ人が `&host=1` を付けて開くと、ホストの ID を先に取れる。対策するには公開鍵でホストを確かめる仕組みが要るので、必要になったら検討する。
- **IP アドレスが相手に見える**: WebRTC の P2P 接続の性質上避けられない。隠したい場合は、TURN の中継だけを使う設定にする必要がある。
- **シグナリングサーバーを信頼している**: PeerJS の公開サーバーは接続の仲介をするだけで、映像やデータの中身は通らない(DTLS で暗号化)。ただし、サーバーが悪意を持てば、仲介の段階で割り込める。気になる場合は自前の PeerServer を立てる(`VITE_PEER_HOST`)。
- **GitHub Actions のバージョンをタグで指定している**(`@v4` など): コミットのハッシュでは固定していない。公式の actions だけを使っているので許容する。
